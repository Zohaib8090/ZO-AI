# Zohara Agent native Android app: parity matrix

Written 2026-11-13 for `apps/android-native` (Kotlin + Jetpack Compose, package `org.zohara.agent`, replaces the Capacitor wrapper `apps/android-web`).
The owner's complaint about earlier conversions: features get forgotten or moved wrongly. So this file is the **contract**: every user-visible
feature, page, setting, control, state, empty state, error state and background behaviour of the desktop app (GTK, `crates/zohara-agent`) and the web
app (`crates/zo-server/web/index.html`), plus what the server expects of a client, is one numbered row. A row is done only when it is
implemented AND verified (tick the last column in the commit that does it, and name the test in the commit message).
The companion file `apps/android-native/docs/API.md` has the request and response shapes.

## How to read it

Columns: **ID** (area prefix + number, stable: never renumber, only append) | **Feature** (what the person sees or what happens; strings are
the real ones from the code) | **Desktop** (`file:function` in `crates/zohara-agent/src`) | **Web** (function:line in `index.html`) | **Phone** (same /
adapted: how / n/a: why) | **P** (must / should / n/a) | **Mod** (module that implements it) | **Done** (`[ ]` open, `[x]` implemented and verified, `[~]` partial: see the parity-check gap list; none are left since 2026-11-13).

* `NEW` in a feature text: part of the owner's list of new features (docs/INTERACTION.md, voice, attachments, paste, link chips,
  notifications, Run on My computer, Claude Code token status, model pins/Address/test, MCP, profiles, hidden providers).
* `(dm)` = exists only in branch `feat/dm` (desktop model chooser, commit 4639fda, file `modelpick.rs`) and `(web2)` = only in `feat/web2`
  (web model sheet, commit 96b8223). Both are being merged into main by another workflow; the native app is built against them. `(main)` = in
  main 8207dd5 (server ops `model_test`, `settings_get`, `settings_set`, `profile_update`, `base_url` and the sync kinds). Everything else is in
  the worktree base 4a488cc.
* `(contract)` = specified in docs but not built in any client or in the service yet (`docs/INTERACTION.md`); the app implements it from the spec and
  tolerates a server that does not send it.
* Modules (disjoint source packages, see the task split): **foundation** (app shell, theme, fonts, logo, navigation drawer, Firebase sign-in,
  API client, DataStore, FCM registration and notification channels, offline banner), **chat** (thread, streaming, composer, tool groups, takes,
  approval and question cards, context panel, permission popover, compact), **pages** (chats list, search, projects, artifacts, scheduled,
  activity, sidebar lists, terminal command box), **settings** (every Settings page, model menu and model sheet, profiles, pins, hidden
  providers, MCP, machines, account, notifications page), **media** (attachments, paste, camera, link chips, share-in, voice in, read aloud),
  **link** (Run on, My computers, desktop events, Claude Code status).
* Sources audited: desktop `crates/zohara-agent/src/*.rs` (main, chat, composer, settings, dock, scheduler, tray, activity_page, quick, shortcut, theme,
  markdown, ask, style.css, `data/zohara-agent-mark.svg`), web `index.html` (2606 lines at 4a488cc), server `main.rs` + `service.rs`, docs
  PUBLIC/LOGIN/SERVER/LINK/INTERACTION/NOTIFICATIONS/SYNC/ACTIVITY/MCP/MEMORY/ANDROID, and the two unmerged branches above.

## Decisions (phone adaptations that are not the same as the desktop or web)

| # | Decision | Reason |
|---|---|---|
| D1 | **No docked terminal and no in-app browser.** The desktop's terminal is a PTY inside the desktop process and the browser is WebKit there; neither is reachable from a phone, and a WebView browser is against the brief (native only). The AI's terminal and browser tool runs still show as tool groups in the chat. The phone gets (a) a monospace, copyable, scrollable **output viewer** for every tool group and for long tool output (rows CHAT-34..36) and (b) the web's one-shot **command box** (`terminal_run`) as a Terminal sheet, admin accounts only and cloud only (rows TERM-*). | Parity with what the web offers; nothing invented. |
| D2 | **Window controls, tray, autostart, global shortcut (Copilot key, Ctrl+Super+C), quick popup, Ctrl +/- zoom, drag handle, WebKit** are n/a. Equivalents: share-in (text, links, pictures, files from other apps become a new message), a static launcher shortcut "New chat", notifications with actions (the tray's "needs attention"), system font scale. | Not meaningful on a phone. |
| D3 | **Sign-in is direct Firebase** (Google through Credential Manager, e-mail and password through the Firebase SDK), exactly like the web, not the desktop's device flow. The phone can also **approve a desktop or terminal sign-in** (the web's `/device` screen) inside the app. | Same as the web; the phone has a real Firebase session. |
| D4 | **No Sync switch and no Sync now.** The phone is a live client of the server, so it has nothing to sync. It shows the web's "Desktop sync" information page (stored counts) and the signed-in devices list. | Desktop-only mechanism. |
| D5 | **Takes (edit and ask again, arrows 2/3), copy whole conversation, Compact** exist on the desktop and are supported by the server (`send.edit`, `switch`, `chat.takes`, `compact`) but not yet by the web. The native app implements them (must) because the owner wants everything the desktop has. | Owner rule: nothing forgotten. |
| D6 | **Context panel** uses the web's client-side estimate (characters / 3.8, window by model name) plus the provider's real `usage` numbers from the stream, because no service op returns the desktop's exact breakdown. Marked as an estimate in the UI, like the desktop's note. | No server op; do not invent one. |
| D7 | **Projects**: the list and "New project" work through the `projects` and `project_create` ops (admin only, as on the web). The desktop's project workspace (instructions, context files, memory, per-project scheduled tasks, project chats that know the project) is stored only in the desktop's own store and has no service op, so it is **n/a until the server exposes it**. | Honest scope. |
| D8 | **Scheduled**: list, cancel and "New task" (`schedule_add` takes plain-words `when`; the server parses it and answers an error text) are implemented; "Run it now", the on/off switch and "Open the last result" need ops that do not exist, so they are n/a (marked). | Honest scope. |
| D9 | **Enter in the message box**: on a phone Enter makes a new line and the send button sends; with a hardware keyboard Enter sends and Shift+Enter makes a new line (as on desktop and web). | Soft keyboards. |
| D10 | **Notifications**: two channels, "Answers" (default importance) and "Needs you" (high). The payload of a push never contains the command or question unless the person turned on "Show details in notifications" (INTERACTION.md section 3). Approval notifications have Allow and Deny actions that call `/api/reply`; question notifications open the question card. | docs/INTERACTION.md, NOTIFICATIONS.md |
| D11 | **Streaming survives the app going to the background**: when push is registered the app sends `keep_running: true`; when the app returns it reloads the chat with `op chat` and shows what the server saved. A dropped connection without `done` is shown as an error row with Try again, never silently. | Mobile lifecycle; `keep_running` exists. |
| D12 | **Hidden providers, pins, Address, Test connection** are built from the (main) ops `providers`, `models {base_url}`, `model_test`, `select {base_url}`, `profile_update`, `profile_pin`, `settings_get/settings_set`. If the server answers "unknown request", the app shows a friendly "This server is too old for that" message and keeps the rest working. | Merge is in flight. |
| D13 | **Question cards and "needs you"** are built from docs/INTERACTION.md. Until the server sends `question` events the cards never appear; the `approval` event is live today. | Contract-first. |
